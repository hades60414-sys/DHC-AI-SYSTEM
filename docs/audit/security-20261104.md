## 1. 已修正的 High

### SEC-WEB-01 — CORS `*` 加上公開註冊：drive-by 網頁 → 首位帳號 → `/shell` RCE（High）

**位置（修正前）**
- `web-ui/server/index.ts:129`：`app.use(cors({ exposedHeaders: [...] }))`。沒設 `origin`，所以回 `Access-Control-Allow-Origin: *`，preflight 也一律放行。
- `web-ui/server/modules/auth/auth.routes.ts:18-33`：`/api/auth/status` 與 `/api/auth/register` 都是公開路由，系統還沒有使用者時就能註冊。
- `web-ui/server/modules/websocket/services/websocket-auth.service.ts:18-60`：WebSocket 升級時沒檢查 `Origin`（WebSocket 不受 CORS 保護）。

**為什麼是 High**：伺服器雖然預設綁 127.0.0.1，但使用者瀏覽器上的任何網頁都能打 `http://127.0.0.1:3001`。認證用的是 bearer header 而不是 cookie，所以註冊／登入回應可以被跨站讀走。拿到 token 後，就能透過 `/shell` WebSocket 執行任意指令。同樣的路徑也能對 `/api/auth/login` 跨站暴力破解密碼（登入沒有速率限制）。

**重現步驟（修正前）**
1. 新安裝（還沒建立帳號）後啟動 server。
2. 在任意網站的 DevTools console 執行：
   ```js
   await (await fetch('http://127.0.0.1:3001/api/auth/status')).json()      // {needsSetup:true}
   const r = await fetch('http://127.0.0.1:3001/api/auth/register', {method:'POST',
     headers:{'Content-Type':'application/json'}, body:'{"username":"evil","password":"evilpass"}'});
   const {token} = await r.json();                                           // 讀得到（ACAO: *）
   const ws = new WebSocket('ws://127.0.0.1:3001/shell?token=' + token);     // 沒有 Origin 檢查
   ws.onopen = () => ws.send(JSON.stringify({type:'init', projectPath:'/tmp', initialCommand:'id > /tmp/pwned'}));
   ```
3. 在本 repo 以 main 的 CORS 設定實測，結果是 `main (before): 200 ACAO= * {"token":"jwt"}`。

**修正**
- 新增 `web-ui/server/shared/origin-policy.ts`，內有 `isOriginAllowed()`、`createOriginGuard()`。請求帶 `Origin` 時，只放行三種來源：
  - loopback（localhost、127.0.0.0/8、[::1]，任何 port；Vite dev 與桌面版在這裡）
  - 同源（Origin 的 host:port 等於 Host header；LAN 或 tunnel 部署）
  - `DHC_ALLOWED_ORIGINS` 列出的精確 origin

  其他一律 403，包括 `null`、`file://` 這類非 http 來源。沒帶 `Origin` 的請求不受影響（curl、Electron 主程序、node `ws`）。
- `web-ui/server/index.ts:132`：guard 掛在所有路由之前，CORS 改為只反射 guard 放行過的 origin（`origin: true`）。
- `websocket-auth.service.ts:35-41`：WebSocket 升級先檢查 Origin，platform 模式也一樣。
- 測試：`web-ui/server/shared/tests/origin-policy.test.ts`。涵蓋 loopback、同源、白名單、`null`、`localhost.evil.example` 這類前綴偽裝；用真的 express server 重現跨站註冊被 403（含 preflight），確認沒有寫入；並驗證 WebSocket 拒絕外來 origin（帶有效 token 或在 platform 模式下都一樣）。

### SEC-WEB-02 — `VITE_IS_PLATFORM=true` 關閉所有認證（High，設定錯誤時）

**位置**
- `web-ui/server/shared/utils.ts:41`
- `web-ui/server/modules/auth/auth.middleware.ts:28-40, 120-131`：platform 模式直接以 `getFirstUser()` 當作 `req.user`

**為什麼是 High**：這個變數名稱看起來是前端用的 `VITE_*`，卻同時控制後端認證，很容易被誤設。`docs/architecture/01-websocket-transport.md:606` 與 `vitest.config.ts` 的註解都寫明這個工作區的 `.env` 設了 `VITE_IS_PLATFORM=true`。這時只要再設 `HOST=0.0.0.0`（程式註解就教人這樣開放給 LAN），區網內任何人不用 token 就能打 REST 與 `/shell`。

**重現（修正前）**：`.env` 設 `VITE_IS_PLATFORM=true` 與 `HOST=0.0.0.0` 後啟動，從另一台機器執行 `curl http://<ip>:3001/api/projects` 會得到 200；不帶 token 連 `ws://<ip>:3001/shell` 也能連上。

**修正**
- `origin-policy.ts` 新增 `checkPlatformModeBinding()`。`web-ui/server/index.ts:347`：platform 模式下綁的是非 loopback 位址時，拒絕啟動（exit 1），並印出原因與三條出路。確實是透過有認證的反向代理部署時，設 `DHC_PLATFORM_TRUSTED_PROXY=1` 可放行。
- platform 模式啟動時一律印出 `[WARN] authentication is DISABLED`。
- 測試：同一個測試檔的 `platform (no-auth) mode refuses non-loopback bind...`。

### SEC-OPS-01 — 中台小助理 guard 可輕易繞過（High）

**位置**：`web-ops/assistant-guard.cjs:18-34`（RISKY_COMMAND）、`:166-171`（修正前只有 Write／Edit 會檢查受保護路徑）

**為什麼是 High**：這支 hook 是同事共用的小助理在執行刪除、對外送出、改 harness 之前，唯一的「確認卡」閘門，範圍也包含 `ragent_cmd` 打到遠端主機的指令。它用 regex 黑名單判斷，但常見寫法完全不會觸發，被 prompt injection 的模型可以不需確認就刪檔、改受保護設定、送出寫入請求。

**重現（修正前）**：在暫存 HOME 下執行
```sh
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"node -e \"require(\\\"fs\\\").unlinkSync(\\\"C:/x.txt\\\")\""}}' \
  | ASSISTANT_ROOT=/tmp/x node web-ops/assistant-guard.cjs ; echo "exit=$?"
# 無輸出、exit=0（放行）；而 `del C:\x.txt` 會被擋
```
新加的 13 個繞過案例在 main 上全部是 `allow`（實測 `FAIL bypass: ... allow` ×13）：`node -e unlink`、`node -e fetch PATCH`、`node --eval writeFile`、`python -c os.remove`、`py -3 -c shutil.rmtree`、`powershell -Command [IO.File]::Delete`、`powershell -enc <base64>`、`move /y ...\ai-tools\approvals\grants\x.json NUL`、`Set-Content ...\approvals\whitelist.txt`、`copy evil.json ...\.claude\settings.json`、`curl --request PATCH`、`curl --json`、`ls && mv a b`。

**修正**（`web-ops/assistant-guard.cjs`）
- RISKY_COMMAND 新增：`Set-Content`／`Add-Content`／`Out-File`／`Tee-Object`／`Move-Item`／`Rename-Item`；出現在指令開頭的 `move`／`ren`／`rename`／`mv`；`curl`／`wget` 的 `--request`、`--json`、`-T`、`--method`、`--post-data`；`powershell -EncodedCommand`。
- `INLINE_CODE` 搭配 `INLINE_DANGER`：`node -e`、`python -c`、`perl -e`、`powershell -Command` 等 inline 程式碼，只有在內容呼叫檔案異動、網路、子程序或 eval API 時才需要確認卡。`python -c "print(1)"`、`node -e "console.log(1)"` 照常放行，維持 10-27「srv-main 可跑 Python」的政策（原測試 `local python` 仍通過）。
- `WRITE_VERB` 搭配 `PROTECTED_PATH`：用 `copy`、`xcopy`、`robocopy`、`cp`、`Copy-Item`、`New-Item`、`mklink`、`icacls`、`attrib`、`takeown`、`tee` 寫入受保護路徑時，也需要確認卡。單純讀取（`type ...\.claude\settings.json`）照常放行。
- 測試：`web-ops/assistant-guard.test.cjs` 新增 13 個繞過案例、6 個「仍應放行」的案例，以及 1 個「確認後可執行」的案例。

**殘餘風險**：regex 黑名單本質上擋不住「先用 Write 寫一支 `x.js`，再 `node x.js`」這種寫法。根本作法是改成白名單，或在 OS 層面用沙箱或權限分離。

### SEC-OPS-02 — 核准單點擊可偽造（High，與 SEC-OPS-01 串連）

**位置**
- `tools/approvals/lib.cjs:7, 29-37`：對 `http://127.0.0.1:3001/api/user/preferences` 讀寫時不帶認證。這只有在 platform（無認證）模式下才能運作，也就證實這個環境跑在那個模式。
- `tools/approvals/run.cjs:17`、`watch.cjs:17`：所謂「點擊」只是比對 `m.by !== 'dhc-assistant' && m.text === '同意核准單 <id>'`，而 `by` 和 `at` 都由客戶端自己填。

**重現（稽核 agent 已在暫存複本上完整跑過）**
1. 對 fake CloudCLI 執行 `ask.cjs`，開出核准單 `8cae22`，內容為 `del /q C:\important\*.txt`。
2. 用一個 fetch PATCH 在聊天室加入 `{by:'x', text:'同意核准單 8cae22', at:<now>}`。
3. 執行 `run.cjs 8cae22`，印出 `done`，fake agent 收到該筆 `ragent_cmd`。正式環境中由 `watch.cjs` 每分鐘自動執行這一步。

再搭配 SEC-OPS-01，被注入的小助理只用一個 `node -e` 就能核准自己開的單。

**本次修正（斷鏈）**：`assistant-guard.cjs` 的 `CHAT_FORGE` 規則。Bash、PowerShell、`ragent_cmd` 指令只要提到 `/api/user/preferences`、`dhc.chat:` 或「同意核准單」，或 Write、Edit 寫入的內容含這些字串，就需要確認卡。測試為 `forge approval click via curl`、`via script file`、`via Edit`。

**仍待處理（根本修正，需設計決定，所以這次沒有改）**：點擊紀錄必須由伺服器在已認證的使用者 session 下寫入並簽章（例如 server-side 的 click 紀錄或 HMAC），`by` 與 `at` 也必須由伺服器決定。在那之前，同機上的任何程式都能偽造點擊。因此修正後降為 Medium。

## 5. 檢查過且判定安全的項目（摘要）

- **web-ui 路由**：`/api/*` 除了 `auth`、`agent`、`browser-use-mcp` 都掛了 `authenticateToken`（`server/index.ts:157-211`）。`/api/agent` 需要 API key；`/api/browser-use-mcp` 需要 32-byte 隨機 token。
- **web-ui 子程序**：git、worktree、ripgrep 都用 argv 陣列且 `shell:false`。少數 `shell:true` 呼叫只帶固定字串。plugin 安裝用 `--` 隔開參數，並加 `--ignore-scripts`。
- **web-ui 檔案操作**：file-tree 用 `resolvePathInsideProject` 確保在專案內；plugin asset 用 realpath 檢查；SQL 全部是 prepared statement；gray-matter 已停用 JS front-matter。
- **Electron**：`contextIsolation`、`sandbox` 皆開啟，`nodeIntegration:false`；preload 只對特定 origin 暴露橋接 API。
- **seal-proxy、Worker gate**：比對採 timing-safe；cookie 用 HMAC；有速率限制，失敗時 fail-closed；非 GET 請求檢查跨 origin。
- **remote-agent**：`SqlActions.cs` 的識別字對照 catalog 並加中括號、值都是參數；`Channel.cs` 用固定憑證、SHA-256 簽章與 AES-256 封裝；`Updater.cs` 由簽章工作檢查 SHA-256，zip 只允許平面檔名。
- **secure-input、grant.cjs、whitelist.cjs、sync-harness.ps1、video-studio setup、pstack hook**：都已檢查，沒發現注入。
- **全 repo**：沒有用到 `Invoke-Expression`。
