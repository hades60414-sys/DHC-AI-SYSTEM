# Autonomous Execution: Practices Distilled from Cloud-Deployment Operations

> English translation of [AUTONOMY.md](AUTONOMY.md). The Chinese original is authoritative. Terminology: [GLOSSARY.md](GLOSSARY.md).

This document brings the reusable practices from a cloud deployment and the interactive testing that followed into DAS; it does not include private conversations, login sessions, cookies or the original host's configuration. The record originally called "GPT operating Vercel" actually used Cloudflare Workers / wrangler; a separate interview about Vercel operations came later. A platform name cannot serve as evidence that a deployment was verified.

## From pickup to completion

1. At the start, state clearly the target resource, what will change, and how it will be accepted; read the project rules and the `.astra` state first. Look up required information in files and the current state first.
2. Within the scope the user has already authorized, complete reversible work, including authorized pushes or deployments, without asking again for the same permission. For outbound operations, payments, permissions and destructive changes that are not yet authorized, prepare a concrete, reviewable change first and then confirm.
3. Keep a Git version or a backup before changing anything; check the source and contents of third-party packages first. Credentials come from local secure settings or environment variables, never from the repo, command output or reports.
4. When a tool is stuck, take stock of resources following the "When blocked" rule in the loaded `AGENTS.md`, keeping the original authorization and acceptance criteria. If the user explicitly says "stop on failure" or restricts the tools, do so; if the result of a write is unclear, read it back first to avoid submitting twice.
5. Before release, check the candidate commit, the build result and the deployed version; after deployment, read the production URL and verify both the HTTP status and the actual content. HTTP 200 by itself does not mean the right version, and a correct screen does not mean the business data is correct.
6. Report in layers: code, tests, build, deployment, live in production, and data verification; state explicitly which layers were not verified. When done, clean up the temporary settings created for this run, and keep the verification evidence and the rollback method.

## Existing mechanisms and how to enable them

| Mechanism | Contents of the public package | Setup required before use |
|---|---|---|
| Claude / Codex behaviour rules | `harness/rules/AGENTS.md`, `CODEX-AGENTS.md` | Sync to the chosen platform; capability still depends on the local tools and authorization |
| Turn-end guard | `harness/hooks/turn-end-guard.js` | A/B basic checks are enabled; the C/D manual-handoff and premature-give-up checks only apply to the workspaces in `das-hooks.json` |
| Resume after approval, timed keep-going | `tools/approvals/`, `keepgoing-detect.js` | Configure the MCP path, the DHC CLI service and the watch schedule; verify wake-up first, then turn on keepgoingEnabled |
| Standing grant | `tools/approvals/grant.cjs` | The user approves a specific command prefix and expiry; this is a mistake-prevention mechanism under the same account, not permission isolation against malicious use |
| Maintenance drain | `harness/hooks/drain-guard.js` | `drainRoot` or `DRAIN_ROOT` points to the actual maintenance service folder |
| Gemini takeover | `tools/gemini-takeover/` | Optional install; the external runner, service and workspace allowlist must be configured separately; EKB integration is not included |

A fresh `~/.claude/das-hooks.json` is generated by the installer, which keeps any existing file. By default workspaces is empty, keepgoingEnabled is false and drainRoot is empty. Fill in the absolute workspace paths you want to enable; each covers only that directory and its subdirectories. toolsRoot points to this repo's tools; update it after moving the repo. If you install only a single hook that depends on the configuration, also copy `das-config.js`.

The approval service uses `APPROVALS_MCP_CONFIG` to specify the local MCP configuration file and `NUDGE_BASE` to specify the DHC CLI service; `WAKE_PROJECTS` can override the Claude conversation directory. These local settings and schedules do not ship with the public package. Until the integration is complete, the presence of the code does not mean the service is usable.

The session list only needs to record the available tools and the scope of authorization, and stays on the local machine; identity verification is left to the user, after which the agent reads back the result and continues. Do not copy login state files or private sessions into a shared package.
