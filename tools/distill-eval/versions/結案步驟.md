# 蒸餾模式：結案步驟（給 Claude）

使用者說「結案」時照這份做。目的：把使用者在這個任務裡展現的工作知識與判斷整理出來，讓下次遇到類似工作時，使用者或幫他做事的 AI 可以直接拿來用。要蒸餾什麼由你依證據決定，不要往特定方向湊。中途不用問使用者。

工具：`node "D:\TAS\Claude Code專案\蒸餾任務\distill.cjs"`
- `sessions`：列出按過燒杯的對話，可以拿來找任務卡漏列的對話。
- `digest "<任務資料夾>"`：依任務卡列的 session id 產生對話摘要到 `結案\素材\`。

## 第一步：盤點素材

1. 使用者說某些對話也屬於這個任務，但任務卡沒列：先加進任務卡。
2. 跑 `digest`。摘要總量超過約 300KB 時，按對話分給子代理抽證據，每個子代理回傳證據清單（格式同第二步），由你合併。
3. 列出素材：對話涵蓋的期間、決策紀錄筆數、往返的文件、版本紀錄、交付物。缺的寫明，例如某段對話紀錄找不到、某封信沒有原文。

## 第二步：抽證據

決策紀錄是主要來源，對話摘要用來補漏與補上下文。記下這類事件，每件附來源：

- 使用者的取捨、否決、堅持，以及當時的理由
- 使用者糾正你或其他人的地方，以及改成什麼
- 花最多時間、重做、來回最多次的地方，以及根因
- 跟其他單位或角色的互動：對方要什麼、問了什麼、在意什麼
- 收到和產出的文件慣例：結構、用詞、格式
- 可以照表重複的步驟
- 學到、下次還用得到的業務、商品、計算或作業知識
- 使用者怎麼跟 AI 協作：怎麼下指令、怎麼檢查、退回過什麼

這些只是找證據的角度，不是章節。

## 第三步：決定主題

把證據歸成主題，依三件事排序：下一個類似的案子還會不會遇到、能省多少時間或來回、證據多強。通常 3 到 7 個；證據不夠就少寫，不要湊數。沒選上的候選列在索引裡，各附一句理由，例如只發生一次、只適用這個案子、證據不足。

同一個工作區以前有結案過的同類任務（`蒸餾任務\<工作區>\*\結案\`），先讀它們的 `00_INDEX.md`：新證據支持舊規則就加註來源，牴觸就兩邊都寫並標明，不要另起爐灶。

## 第四步：寫知識檔

寫到 `結案\`，繁體中文 Markdown，一個主題一份：`01_<主題>.md`、`02_<主題>.md`……

每份主題檔包含：
1. 開頭一句話：這份解決什麼問題、什麼時候該讀。
2. 本體：用最合適的形式，可以是規則、清單、表格、流程、範本或句型。寫成通用做法，這個任務只當例子。
3. 當時的做法和事後看更好的做法如果不同，兩個都寫，並標明哪個是哪個。
4. 檔尾「本案附錄」：只適用這個任務的細節放這裡。

`00_INDEX.md` 包含：素材盤點結果；選了哪些主題、為什麼，沒選的候選和理由；什麼情況讀哪一份的對照表；第五步三項驗證的結果；最多 10 個要使用者確認的問題，每題附你的最佳猜測，讓他只要回「對」或「不對，應該是…」。

寫作規則：
- 每條規則句尾標來源，例如〔決策 10/06 14:05〕〔對話 10/05〕〔往返 信件 10/02〕〔版本 V6〕。沒有來源的推論標「（未確認）」；只出現過一次的做法標「（單次）」，不要寫成慣例。
- 去識別：只寫角色，不寫人名、客戶、交易對手，也不寫實際的金額、部位、價格。捨入位數、計息基礎這類計算慣例可以寫。引用原文只用 20 字以內的短句。
- 同一件事在不同檔案用同一個編號（例如 K-07），方便互相查。
- 寧可少而準：每份大約 200 行以內，刪掉放到任何案子都成立的空話。

## 第五步：驗證

1. 留出測試：歸納判斷類規則之前，先挑 2 到 3 個有紀錄、知道使用者實際怎麼選的決定放到一邊，不拿來歸納。寫完規則後用規則去預測它們，寫下預測、實際和落差原因。可以修規則，但要報修正前的命中數。這類紀錄不到 2 個就寫明並跳過。
2. 回放測試：假裝今天是這個任務的第一天，手上只有當時拿得到的東西加上這份蒸餾。逐條檢查實際發生過的重做、卡關和來回，看有幾件能提前避免或提前問出來，報出比例（例如 11/16），擋不到的寫原因。這只證明有涵蓋到，不代表預測得準，照實寫。
3. 冷讀測試：開一個沒看過素材的子代理，只給它 `結案\` 的檔案，問它「下一個類似的新案子進來，第一週要做什麼、要先跟誰確認什麼？」答不出來或答錯的地方補進檔案。開不了子代理就自己作答，並註明這個測試偏弱。

## 第六步：技能草稿

寫 `結案\skill\<技能名>\`：技能名用小寫英數與連字號（例如 `structured-note-valuation`）。裡面放：
- `SKILL.md`：開頭 YAML frontmatter，`name` 同資料夾名，`description` 一兩句寫「什麼時候該用」（下次 AI 只看這句決定要不要載入，要寫出會觸發的工作類型與關鍵詞）。本體寫：適用範圍、開工清單（先確認什麼、先問誰）、核心規則（引用編號）、常見坑、交付前檢查。本體控制在 150 行以內，細節指向同資料夾的主題檔。
- 第四步的主題檔各複製一份，讓技能資料夾自己就看得懂、可以整包帶走。

同一個工作區已經有上架的同類技能（`<cwd>\.claude\skills\`）就改寫成更新版，不要另開一個。有 writing-for-agents 或 skill-creator 技能可用時，照它們的寫法。

## 第七步：回報與上架

1. 任務卡狀態改「已結案」，寫上結案日期與 `結案\` 檔案清單。
2. 回覆使用者（先講結論）：選了哪些主題和理由、三項驗證結果、待確認問題、技能草稿的位置，並問要不要上架。
3. 使用者回答待確認問題後，直接更新知識檔與技能，拿掉已確認的「（未確認）」。
4. 使用者同意上架才做：把 `結案\skill\<技能名>\` 整個複製到這個工作區的 `<cwd>\.claude\skills\<技能名>\`，只有在這個工作區開的對話會載入。要給 Codex 用，就把同一個資料夾放到那台電腦的 `~/.codex/skills/`。
