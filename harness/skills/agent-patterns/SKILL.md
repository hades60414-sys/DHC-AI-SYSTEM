# agent-patterns — 選對模式,再開工

> 沒有最好的模式,只有最小且夠用的組合。多數任務的正解是「直接做」。

## 1. 開工閘(30 秒內答完)

依序問,任一答「是」才往下設計;全部「否」→ 直接做(ReAct),不要輸出設計。

1. **錯誤代價高?** 金額/數字結論、不可逆動作、對外交付、合規。→ 加驗證類模式(§2 的 V 欄)
2. **品質要反覆打磨?** 報告、文案、程式重構、prompt。→ 評估-優化迴圈
3. **可拆成互不依賴的子工作?** 多來源研究、多模組、多視角審查。→ 交給 `baton-dispatch` 決定分工形狀
4. **流程固定、會重跑?** 日更/批次/同質大量項目。→ 固定 workflow(prompt chain / batch),不要讓 agent 自由發揮
5. **輸入類型差很多、成本敏感?** → 路由/級聯(便宜模型先,不確定才升級)
6. **要跨 session 累積知識?** → 記憶模式(本 harness 已有 memory / `baton` 交接)
7. **是在設計一個給本地小模型跑的系統?** → 讀 [references/local-models.md](references/local-models.md)

## 2. 模式速查表

| 情境 | 首選模式 | 最小實作(本 harness) | V(驗證)? |
|---|---|---|---|
| 一次能答完、資料在手 | 1 增強單次呼叫 | 直接答 | |
| 路徑不固定、要邊看邊做 | 2 ReAct | 預設工作方式 | |
| 輸入類型多、要控成本 | 3 路由 / 級聯 | scout(便宜)→ executor → 主模型;Codex lane 分級 | |
| 長流程、可預先拆步 | 4 規劃-執行 | Plan agent → executor/mech-executor;plan-verifier 審計畫 | |
| 品質要求高、可客觀批評 | 5 評估-優化 | 生成 → 獨立 subagent 依 rubric 批評 → 改寫,≤3 輪 | ✓ |
| 不可逆 / 錢 / 合規 | 6 驗證閘 | verifier / codex-verifier;人工核准點 | ✓ |
| 跨領域長期協作 | 7 多代理 + 共享記憶 | 優先「獨立 worker + 主模型整合」,真的要互相辯論才用 team | |
| 大量外部系統操作 | 8 工具使用代理 | MCP / skill;工具說明寫清楚比加 agent 有效 | |
| 分類/判斷要穩定 | 9 自洽 / 投票 | 同題 N 次(或 N 模型)→ 多數決/合併;分歧本身是訊號 | ✓ |
| 要記住偏好、長期累積 | 10 情境記憶 | memory 系統、`.baton/` 交接、專案 HANDOFF 檔 | |
| 解空間大、要回溯 | 搜尋式推理(ToT/LATS/best-of-N) | 多候選 + 評分器挑選;只在有可靠評分器時用 | ✓ |
| 要找出最佳 agent 設計本身 | 自動化設計(ADAS/AFlow/DSPy) | 先有 eval 集,再讓模型改流程;沒 eval 集不要做 | ✓ |

## 3. 常見組合(從場景出發)

- **中台數字結論**(對帳、P&L、風險):ReAct 做 → 獨立重算(自洽的變形)→ 驗證閘;對不上報 break,不收斂到「看起來合理」。
- **研究報告**:規劃拆題 → 平行 worker 各查一面(`baton-dispatch`)→ 主模型整合 → 評估-優化 1–2 輪。
- **程式大改**:規劃-執行 + 測試當驗證器;評分器 = 測試,不是另一個 LLM 的意見。
- **本地模型批次分類**:路由(規則先、模型後)+ 固定 schema 輸出 + 自洽投票 + 低信心轉人工。

## 4. 產出格式

需要設計時,開工前只輸出一行(或最多一個小表),然後照做:

`模式: <組合> | 理由: <觸發的閘題號> | 驗證: <誰/什麼判定完成> | 預算: <輪數/agent 數上限>`

分工細節(誰寫哪些檔、幾個 worker)交給 `baton-dispatch`;不要在這裡重做。

## 5. 紅線

- 模式是手段:加一層 agent 必須換到可說出的好處(品質、速度、成本、隔離),否則刪掉。
- 評估-優化、自洽、搜尋只在**評分標準可說清楚**時有效;沒有 rubric/測試/規則就只是多花 token。
- LLM 當評審會偏好自己的輸出與長答案;高風險判定用規則、測試、獨立重算或人,LLM 評審只當輔助。
- 迴圈一律設上限(輪數、token、無進展即停),沿用 `baton-dispatch` 的停止條件。
- 多代理的主要失敗來源是規格不清與交接遺漏,不是模型不夠強:先寫清楚契約再分工。
