# 核心模式細節(10 基本型 + 2 延伸)

每個模式:機制 → 何時用 → 成本 → 失敗模式 → 本 harness 對應。
「成本」以單次 LLM 呼叫 = 1x 粗估,只作比較用。

## 1. 增強單次呼叫(Augmented LLM)
- 機制:一次呼叫,掛檢索、工具、短期記憶;無迴圈。
- 何時:摘要、欄位擷取、格式轉換、資料在手的問答。
- 成本:1x。
- 失敗:檢索錯就整題錯,且沒有自我修正機會。
- 對應:直接回答。這是所有模式的積木,先把它做好(好的工具說明、好的檢索)再談架構。

## 2. ReAct(思考→行動→觀察 迴圈)
- 機制:推理與工具呼叫交錯,依觀察結果決定下一步,直到完成。
- 何時:路徑事先不知道的任務(除錯、查資料、探索 repo)。
- 成本:步數 × 1x,不可預測。
- 失敗:繞圈、過早宣告完成、被錯誤觀察帶偏。需步數上限與完成條件。
- 對應:Claude Code 預設工作方式。

## 3. 路由 / 級聯(Router / Cascade)
- 機制:先分類意圖或難度,再導向不同模型/流程;級聯版 = 便宜模型先答,信心不足才升級。
- 何時:輸入異質、量大、成本敏感。
- 成本:分類 0.1–1x + 被選路徑。
- 失敗:分錯路比答錯更難察覺;要記錄路由決定並抽查。規則能分的先用規則。
- 對應:scout / mech-executor / executor / 主模型分級;Codex scout(Luna)/worker(Terra)/verifier(Sol)。

## 4. 規劃-執行(Planner-Executor / Orchestrator-Workers)
- 機制:先產計畫(步驟、依賴、驗收),再由執行者逐步或平行做,最後整合。靜態版計畫固定(Plan-and-Solve、ReWOO);動態版由 orchestrator 依結果改計畫(Magentic-One 的 task/progress ledger)。
- 何時:長流程、可拆解、需要在開工前讓人看過計畫。
- 成本:計畫 1–2x + 執行。
- 失敗:計畫在第一個意外就過時;要允許重新規劃,並在 plan 寫停止條件。
- 對應:Plan agent → plan-verifier → executor;分工形狀交 `baton-dispatch`。

## 5. 評估-優化(Evaluator-Optimizer / Self-Refine / Reflexion)
- 機制:生成 → 評審依 rubric 批評 → 改寫,重複 2–3 輪。Reflexion 版把失敗教訓寫進記憶供下次用。
- 何時:對外文件、報告、程式碼品質、prompt 打磨;評分標準說得清楚時。
- 成本:(1 + 評審)× 輪數,約 3–6x。
- 失敗:同一模型自評常只修表面;評審偏好長答案;超過 3 輪多半無進展。
- 實作要點:評審用**不同 context**(獨立 subagent)或不同模型;rubric 事先寫死;每輪只改被點名的問題;無實質變化即停。
- 對應:生成後派 verifier 或 fresh subagent 依 rubric 審,主模型改。程式碼用測試當評審。

## 6. 驗證閘(Verifier-Gated)
- 機制:產出先過獨立驗證(規則、測試、另一模型、人),通過才執行,否則退回或升級人工。
- 何時:付款、授權、合規、刪除、部署、對外發送、數字結論。
- 成本:1x + 驗證。
- 失敗:驗證器與生成器同源同盲點;驗證只查格式不查語意。
- 對應:verifier / codex-verifier(異質模型);CLAUDE.md 安全紅線的「先問我」即人工閘。

## 7. 多代理 + 共享記憶
- 機制:多個專精 agent 經由協定(A2A)或共享記憶/黑板協作。
- 何時:真正跨領域、各自需要大量獨立 context 的長期工作。
- 成本:業界實測多代理約為一般對話的 ~15x token(Anthropic 研究系統,見 research-catalog)。
- 失敗:規格不清、角色越權、交接漏資訊、互相附和、沒人負責收斂(MAST 失敗分類)。
- 對應:優先「平行獨立 worker + 主模型整合」;真的要互相挑戰才用 team。共享記憶要有治理(誰能寫、何時失效)。

## 8. 工具使用代理
- 機制:由 LLM 選擇並組合多個工具(檢索、DB、程式、系統操作)。
- 何時:需要跟外部系統互動。
- 失敗:工具太多選錯;工具說明模糊;副作用工具被誤呼叫。
- 實作要點:工具少而清楚;有副作用的工具加確認;CodeAct 變形 = 讓模型寫程式碼當動作,組合能力強但要沙箱。
- 對應:MCP、skill、Bash;公司環境限制見 `company-environment`。

## 9. 自洽 / 集成投票(Self-Consistency / Ensemble)
- 機制:同題生成 N 個候選(同模型不同取樣,或不同模型),投票或由評審合併。
- 何時:分類、判斷、單一答案題;要降低偶然錯誤。
- 成本:N x(N 常用 3–5)。
- 失敗:系統性錯誤不會被投票消掉(全部錯同一個方向);開放式長答案難投票(用 Universal Self-Consistency:由模型挑最一致的)。
- 實作要點:**分歧率本身是信心指標**——全數一致才自動通過,有分歧轉人工或加深分析。
- 對應:數字結論用「兩條獨立路徑重算」;本地小模型分類特別適用。

## 10. 情境記憶(Memory-Augmented)
- 機制:依情境檢索長期記憶,結束時寫回摘要/結構化事實。
- 何時:個人化、長期專案、多輪累積。
- 失敗:記憶過時被當事實;記憶膨脹導致檢索雜訊;寫入未審的錯誤。
- 對應:memory 系統(frontmatter + 索引)、`.baton/` 交接、專案 HANDOFF 檔。規則:記憶是線索,引用前先驗證現況。

## 11. 搜尋式推理(Tree/Graph of Thoughts、LATS、best-of-N + 評分器)
- 機制:展開多條推理分支,用評分器(PRM、測試、規則)剪枝或回溯。
- 何時:解空間大、有可靠評分器(程式有測試、數學有檢查、規劃有模擬)。
- 成本:10x 以上常見。
- 失敗:評分器不可靠時等於昂貴的隨機;一般業務任務很少值得。

## 12. 自動化 agent 設計(ADAS、AFlow、DSPy 最佳化)
- 機制:以 eval 集為目標,讓模型搜尋/改寫 prompt、流程與模組組合。
- 何時:同一個 pipeline 會長期大量跑,且有標準答案可評分(例:本地模型分類、信評模型 類型評等解釋)。
- 前提:先有 eval 集與 baseline;沒有就先建 eval,不要先調架構。
- 失敗:過擬合 eval 集;要保留 holdout。

## 組合規則

- 由內而外加層:先把 1 做好 → 需要才加 2 → 有風險才加 6 → 要品質才加 5/9 → 真的可拆才加 4/7。
- 每加一層都寫下:它解決什麼失敗、怎麼知道它有效、上限在哪。
- 評分器優先序:確定性檢查(測試/規則/重算)> 異質模型 > 同模型 fresh context > 同模型同 context。
