# 本地小模型(≈1–14B)的模式選擇

原則:小模型的弱點是長鏈推理、長 context、自由格式與自我批評;強項是便宜、可多跑、可重複。
所以架構要**把推理搬到程式、把模型限縮成窄判斷、用多次取樣換穩定**。

## 適合度

| 模式 | 小模型適合度 | 說明 |
|---|---|---|
| 增強單次呼叫(窄任務、固定 schema) | 好 | 小模型的主戰場:分類、擷取、正規化 |
| 路由 / 級聯 | 好 | 規則先過濾 → 小模型 → 低信心升級大模型或人 |
| 自洽投票 | 好 | 便宜到可以跑 3–5 次;分歧率當信心 |
| 驗證閘(確定性) | 好 | 程式檢查格式、範圍、衝突、新鮮度;模型不做 guard |
| 固定 workflow / prompt chain | 好 | 每步窄、步間由程式傳遞與檢查 |
| 規劃-執行 | 中 | 計畫交大模型或寫死;小模型只執行單步 |
| ReAct 自由迴圈 | 差 | 容易繞圈、幻覺工具、提早宣告完成;要硬步數上限 |
| 自我反思 / 自評優化 | 差 | 小模型自評常附和自己;改用程式或大模型評審 |
| 多代理辯論 | 差 | 成本與協調失敗放大,收益少 |
| 搜尋式推理(ToT/LATS) | 差,除非 | 只有在評分器是確定性程式時才可用 |
| 自動化設計(DSPy/AFlow 類) | 好(離線) | 用大模型或最佳化器調小模型的 prompt/流程,小模型只負責執行 |

## 實務規則

1. **確定性層優先**:重複鍵、格式正規化、日期/新鮮度、來源衝突、目標狀態已變 → 寫程式,不交給模型。小模型的「看起來成功但其實錯」多半落在這幾類。
2. **輸出契約簡單**:短 JSON、少欄位;列舉值用模型自然會寫的字(不要用選單編號或自創碼)。受限選單介面在小模型上可能反而大幅降低正確率——先用小樣本實測再決定。
3. **格式失敗 ≠ 能力為零**:模型回吐輸入或壞格式時,先做格式診斷(少量呼叫),再判斷能力。
4. **候選清單要小心**:給小模型有限候選時,它傾向挑「看起來合理」的干擾項;要有「以上皆非 / 不確定」出口。
5. **信心出口**:自洽分歧、schema 驗證失敗、guard 命中 → 轉人工或升級大模型,不要自動重試到過。
6. **順序**:先選模型與架構 → 再調工具介面 → 最後才考慮微調。有 eval 集才比較。
7. **eval 紀律**:事先登記指標與樣本(pre-registration);作者自出的題與 gold 同函式產生時,結果只算一致性,不算正確率;保留 holdout。
8. **常駐程序**:本地推論服務的存活方式要先確認(session 結束可能被回收);持久化屬外部副作用,先取得同意。

## 典型骨架

```
輸入 → 規則前處理/過濾 → 小模型(窄任務, 固定 schema)×N 取樣
     → schema 驗證 + 確定性 guard → 一致?→ 通過
                                   → 分歧/失敗 → 大模型或人工
```
